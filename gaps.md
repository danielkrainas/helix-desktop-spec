# Gaps

Living log of missing, unclear, or underspecified contracts.

## Open gaps

- `org.gnome.Shell.Screenshot`: which callers GNOME allows (Helix allows its portal backend and `org.gnome.Screenshot`), the D-Bus error for a cancelled `SelectArea` / `PickColor` (Helix: `org.freedesktop.DBus.Error.Failed`), what happens when the file name is taken (Helix adds ` (2)` etc.), and the pixel scale of captures spanning monitors with different scales (Helix uses the highest) are undocumented. GNOME's screenshot UI (window selection, screen recording, copying to the clipboard) is much richer than Helix's; Helix captures an area or the whole screen.
- Screenshot portal: where GNOME's backend saves non-interactive screenshots, and when it asks the user, are undocumented. Helix asks (shows its screenshot UI) unless the frontend says the app's permission was checked, and saves in the `Screenshots` folder. Helix offers no "window the user picks" target.
- Screen casting: which callers mutter lets use `org.gnome.Mutter.ScreenCast`, and its stream formats and frame pacing, are not documented here; Helix's are in `org.gnome.Mutter.ScreenCast.md`. Helix records monitors and windows (no areas or virtual monitors), has no cursor metadata, remembers only shared monitors (not windows) for `persist_mode`, and does not offer `org.gnome.Mutter.RemoteDesktop`. The contents of GNOME's `restore_data` are its own; Helix's are in `org.freedesktop.impl.portal.md`.
- DisplayConfig: D-Bus error names for rejected `ApplyMonitorsConfig` calls (Helix uses `org.freedesktop.DBus.Error.InvalidArgs` for stale serials and invalid configurations); per-monitor `properties` keys in `ApplyMonitorsConfig` (Helix ignores them); how GNOME's own confirmation of persistent changes is triggered (it happens inside gnome-shell; Helix uses its own `org.helix.DisplayChangeDialog`) and whether GNOME also asks after temporary changes; fractional scales; CTM semantics, and whether GNOME keeps gamma ramps across mode changes; whether GNOME's `Backlight` serial changes when a value changes, and the `min` it reports for kernel backlight devices (Helix: serial changes only with the set of entries; `min` 1). Helix does not implement `ChangeBacklight` (deprecated), `SetOutputCTM`, or DDC/CI backlights.
- Which input counts as "user activity" for IdleMonitor (e.g. whether pointer motion without buttons does). Helix counts every input event.
- Session startup ordering in GNOME 51 (gnome-session's systemd targets) is not documented here. Helix uses its own simple launcher; components announce readiness by owning a bus name or calling `SessionManager.Setenv` (the compositor sets `WAYLAND_DISPLAY`).
- Input settings Helix does not apply yet: `ibus` input sources, `per-window`, custom pointer acceleration (`custom-accel-config`), `scroll-speed`, and the trackball, pointing stick, tablet and touchscreen schemas. The input source switcher shows source ids, not their descriptive names.
- SessionManager D-Bus error names are unspecified. Helix uses `org.gnome.SessionManager.Error.{NotInInitialization,AlreadyInitialized,NotInRunning,NotRegistered,InvalidCookie,InvalidArgs,Inhibited,General}` pending a contract.
- SessionManager inhibitor/client lifetime: Helix drops a caller's clients and inhibitors when its bus connection goes away (so a crashed app can't block logout forever). Not specified by the contract.
- SessionManager `CanShutdown` / `CanReboot` / `CanSuspend` return a `u` availability whose values are undocumented. Helix does not implement them; its shell asks logind (`CanPowerOff` etc., whose answers are documented) instead.
- SessionManager session-restore API (`RegisterRestore`, `DeletedInstanceIds`, `UnregisterRestore`): semantics of `reason`, `instance_id` and `cleanup_ids` are undocumented. Helix sets `RestoreSupported` to false and does not implement them.
- Whether `Setenv` values must also reach the systemd user manager's environment (GNOME runs its session as systemd user units). Helix does not use systemd units and only updates the D-Bus activation environment.
- `org.gtk.Notifications` `ActionInvoked` signal (added in GNOME 51): when GNOME Shell emits it relative to activating the app over `org.freedesktop.Application` is undocumented. Helix activates the app and does not emit it.
- `org.gnome.SessionManager.EndSessionDialog` `Open` type values beyond 0 (logout), 1 (power off) and 2 (restart) are undocumented (GNOME also has upgrade-related dialogs). Helix only uses 0–2.
- Portal backend requirements beyond the standard XDG portal interfaces (GNOME-specific impl details).
- Settings portal: namespaces beyond `org.freedesktop.appearance` are undocumented, yet GTK reads `org.gnome.desktop.interface` (and others) through the portal when sandboxed. Which namespaces and keys a GNOME-compatible backend must expose is not in the spec; Helix's set is in `org.freedesktop.impl.portal.md`. GNOME's own mapping from `accent-color` names to sRGB is not documented either; Helix uses the colors libadwaita documents for `AdwAccentColor`.
- Settings / Session portal backends: the value of the `version` property each backend should report is undocumented. Helix reports 1.
- Shell extension API surface (explicitly deferred; internal and unstable).
- `org.gnome.Shell` grab flags (`grabFlags` values beyond 0) are undocumented.
- Window switching: GNOME's exact grouping and ordering rules for `switch-applications` (e.g. whether activating an application raises all its windows, and moving into an application's windows from the application switcher) are not documented here; Helix's rules are in `contracts/wayland/README.md`. Helix does not implement `cycle-windows` / `cycle-group` (switching without a popup) or `switch-panels`.
- Window placement across monitors: mutter's rules (where new windows open, what happens to windows of a monitor that goes away) are not documented here; Helix's are in `contracts/wayland/README.md` ("Monitors and windows").
- Workspaces: GNOME's exact rules for dynamic workspaces (e.g. when an emptied workspace is removed, focus after switching) and for `workspaces-only-on-primary` are not documented here; Helix's are in `contracts/gsettings/workspaces.md`. Helix lays workspaces out in a row, so the `-up`/`-down` workspace keys do nothing; it has no workspace overview, no `toggle-on-all-workspaces`, no `workspace-names`, and no workspace switch popup.
- Night Light: how GNOME turns a color temperature into gamma ramps, how it fades, and when it re-checks the schedule are undocumented; Helix's choices are in `contracts/gsettings/night-light.md`. gnome-settings-daemon's `org.gnome.SettingsDaemon.Color` D-Bus interface (`NightLightActive`, `Temperature`, `DisableUntilTomorrow`, used by Settings and the shell's quick settings) is not offered, and Helix does not update the location through GeoClue.
- Brightness and volume keys: GNOME's brightness step, which monitor the `screen-brightness-*-monitor` keys mean by "current monitor", the step of the `-precise` volume keys and the OSD icon thresholds are undocumented. Helix: brightness steps of 1/20 of the range on every controllable monitor (the `-monitor` keys act the same), precise steps of 1 percent, icons switching at 33 and 66 percent (`contracts/gsettings/shell-keys.md`). Playback keys go to MPRIS players (Helix's choice of player is in `org.mpris.MediaPlayer2.Player.md`); gnome-settings-daemon's `org.gnome.SettingsDaemon.MediaKeys` (`GrabMediaPlayerKeys`, used by apps to receive the keys themselves) is not offered, and other media keys (calculator, email, search, …) are not handled.
